# v0.1.1 capability and grouping qualification

This version completes the scoped headless implementation documented in the
[README](../../README.md) and [usage contracts](cuda9-usage-contract.md).
Earlier CUDA-9 notes describing README/release work as deferred are historical;
the public entry point is now updated. No rendering, sensor, collision-engine,
shared swarm reward or inter-agent dynamics implementation is implied.

## Parallelism and interpretation

N=E*A independent agent lanes. Dynamics launches use 128 threads per block with
one lane per thread; multiple blocks execute across GPU multiprocessors. Each
thread fuses an agent's motor/integration work, whose integration stages have
sequential dependencies. An environment is not assigned a single CUDA thread.
Changing E/A at fixed N does not serialize its agents or change equations.
Some arena metadata scales with E, but physical-state work scales with N.

The CPU comparison deliberately parallelizes individual agents within the single
environment, using original QuadrotorEnv instances, not a serial swarm proxy.
It measures independent dynamics/task semantics; no collective interaction cost
is present on either backend. CPU group labels are organizational only.

## Matched RL measurements

Same RTX 5070 Ti / Ryzen 9800X3D and workload as the
[CUDA-9 evidence](cuda9-validation.md): 32 steps, GAE, two PPO epochs, fixed matched
weights/noise and initial takeoff. Nine samples after three warmups. CPU physics
uses 1/8 threads or persistent processes; policy/learner runs either on CPU
(one Torch thread) or GPU (eight host threads). These are best tested settings,
not an exhaustive CPU tuning claim. Numerical downstream and symmetric 1.15x
GPU timing-bracket gates passed for all four retained runs.

## Next optimization decisions

- First scale total N; current agent-level parallelism already exploits swarm
  batches. Splitting one small agent across threads is not automatically faster:
  integration dependencies, communication and extra storage can erase gains.
- Measure register pressure/occupancy at large N before changing dynamics
  mapping. The existing fused dynamics kernel has a high register budget; test
  alternative block sizes or cooperative mappings against the same parity gates.
- At small N, policy/history launch overhead dominates; investigate whole-rollout
  submission/capture only with retained stream/lifetime and transfer guarantees.
- Large RL capacity is constrained by T*N history and learner activations. The
  earlier 16,384-agent PPO iteration peaks around 1.2 GB Torch memory. Do not
  extrapolate the 578 MB simulator arena into a million-agent PPO memory claim.
  Chunked/minibatched learner work needs its own equivalence and throughput gates.

## Reproduction and release boundary

After setup and local verify, use the CUDA-9 RL benchmark command with
`--lanes 1000 --agents 1000 --workers 1,8 --samples 9 --warmup 3
--cpu-policy-devices cpu,cuda:0 --cpu-learner-threads 1` for one swarm environment;
substitute `--agents 1` or `--agents 100` for equivalent groupings. Defaults retain
both thread/process modes, 32 steps and two PPO epochs. `--trace` now forwards
the same grouping to the independent trace collector.

Simulation probe: `python3 -m flightmare_profile --workloads environment-graph
--cases 1x100,1x1000,100x1,1000x1,10x100,256x1024,1024x1024
--iterations 20 --samples 5 --warmup 5 --reset-percent 50` inside the container
with `PYTHONPATH=/workspace/flightmare-profile`.

The implementation is versioned locally as 0.1.1. Release validation is a local
clean-checkpoint check; no remote publication, push or tag is implied. Existing
sanitizer/WDDM and multi-GPU coverage limitations remain explicit.
